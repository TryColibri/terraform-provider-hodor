# hodor_integration (Data Source)

An integration of the workspace's catalog, a global one or one private to the workspace, found by exactly one of `id`, `slug` or `name`. A `hodor_connector` installs it in the workspace by its `id`. Its `tools` are what a contract version's permission set names, so `tools = data.hodor_integration.x.tools` lists every tool in the plan; a tool the catalog gains later shows in the next plan as a new version, and is granted only once that version is in force.

## Example Usage

```terraform
# The Notion entry of the workspace's catalog, found by its slug. Name it by
# exactly one of slug, name (name = "Notion", as the catalog shows it) or id
# (id = "int_k3x9q2m1abCD", as GET .../integrations lists it).
data "hodor_integration" "notion" {
  slug = "notion"
}

# A connector installs the integration in the workspace, by its id.
# Without a key it is installed but cannot call Notion: give it one with
# api_key_wo, as hodor_connector's example does.
resource "hodor_connector" "notion" {
  integration = data.hodor_integration.notion.id
  scope       = "shared"
  # A connector's name takes letters, digits and single `_`, which an
  # integration's name may not: name it yourself.
  name = "Notion"
}

# The members the contract serves: a version that names no group grants no one.
resource "hodor_group" "support" {
  name = "Support"
}

resource "hodor_contract" "support" {
  name = "Support"
}

# Every Notion tool, named one by one in the plan. A tool the catalog gains
# later shows in the next plan as a new version, granted only once applied.
# To grant fewer, list the names you want instead. Until this version is
# applied, the contract grants nothing.
resource "hodor_contract_version" "support" {
  contract_id = hodor_contract.support.id

  permission_sets = [
    {
      connector_id = hodor_connector.notion.id
      tools        = data.hodor_integration.notion.tools
    },
  ]
  group_ids = [hodor_group.support.id]
}
```

## Find an integration's id

A connector names its integration by id: `int_` followed by 12 letters and digits, case-sensitive, such as `int_k3x9q2m1abCD`. The same integration has another id in another Hodor environment, so a configuration reads the id rather than writing it down where it can:

- In the configuration, with this data source: `data.hodor_integration.x.id`, the integration found by its `slug` (`notion`, the prefix of its tools' names) or its `name` (`Notion`, as the catalog shows it). Two integrations may share a name; the read then fails and lists both, with their ids and slugs: name the one you mean by `slug` or `id`.
- With the workspace API key, before writing the configuration: `GET /v2/workspaces/{workspace_id}/integrations` lists every integration the workspace's catalog shows, the global ones and the workspace's own, each with its `id`, `slug`, `name` and `kind`.

  ```shell
  curl -s -H "Authorization: Bearer $HODOR_API_KEY" \
    "https://api.hodor.ai/v2/workspaces/$HODOR_WORKSPACE_ID/integrations"
  ```

- In the Hodor app: Connectors > New Connector, then open the integration. Its id is under its name, with a button that copies it.

An id names exactly one integration, as written. An integration the workspace's catalog does not show, one hidden there included, fails the read.

## Schema

### Optional

- `id` (String) The integration's id, `int_` followed by 12 letters and digits, e.g. `int_k3x9q2m1abCD`: what a `hodor_connector`'s `integration` names. Set it to read that integration, matched as written, case included; otherwise it is the id of the one found by `slug` or `name`. An id the workspace's catalog does not show fails the read.
- `name` (String) The integration's name, as the catalog shows it, e.g. `Notion`. Set it to find the integration by name, matched without regard to case and kept as written; otherwise it is the catalog's. A name no integration has, or that two have, fails the read: name it by `id` or `slug` instead.
- `slug` (String) The integration's slug in the catalog, e.g. `notion`, the prefix of its tools' names. Set it to find the integration by slug, matched without regard to case and kept as written; otherwise it is the catalog's. A slug the workspace's catalog does not show fails the read.

### Read-Only

- `auth_type` (String) How a connector of it signs in to the integration, as the catalog records it, e.g. `oauth`, `api_key` or `none`.
- `description` (String) What the integration does; empty when the catalog says nothing.
- `kind` (String) How Hodor reaches it: `mcp`, an MCP server, or `api_wrapper`, an HTTP API Hodor serves as tools.
- `scopes` (Set of String) The scopes a `hodor_connector` of it may take, from `shared` and `personal`.
- `tools` (Set of String) The names of its tools in the catalog, the names a permission set's `tools` takes (`hodor_contract_version`, `hodor_permission_set`). They are the tools every connector of it starts from, before a connection brings its own.
